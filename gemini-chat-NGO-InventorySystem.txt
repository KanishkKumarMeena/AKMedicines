Response: Project Title: AK Medicines: Transaction-Driven Inventory & Alert System for Medical NGOs
Architecture & Tech Stack
* Frontend: React (Handles the dashboard UI, data upload components, and transaction forms).
* Backend: Flask (Python REST API managing business logic, transaction processing, and automated email dispatches).
* Database: PostgreSQL or SQLite (via SQLAlchemy) to store the ledger and inventory states.
Core System Workflows
1. Initial Data Ingestion (The Baseline) NGO staff onboard onto the system by uploading their current inventory. This can be handled via a bulk CSV upload or manual data entry forms in React. The database captures granular details:
* Medicine Details: Brand name, quantity, and expiration dates.
* Salts / Active Ingredients: Tracking salts is a critical architectural decision. If a specific brand runs out, the system can identify alternative brands in stock with the exact same salts, or suggest vendors that sell generic equivalents.
2. Ledger-Based Transaction Tracking Rather than directly overwriting a "quantity" cell in a database, AK Medicines uses a transaction logging approach.
* Staff log discrete events: Dispensing (e.g., "Issued 50 units of Amoxicillin to Mobile Clinic A") or Receiving (e.g., "Intake of 200 units from Donor X").
* The Flask backend dynamically calculates the current on-hand stock by summing these transactions. This provides the NGO with an immutable audit trail, preventing untracked inventory shrinkage or mismanagement.
3. Automated Audits & Alerts The Flask backend routinely checks the dynamically calculated stock against predefined safety thresholds.
* Expiring Stock: Flags medicines approaching their expiry date so the NGO can prioritize dispensing them.
* Depleted Stock: Triggers an email alert via the Flask backend. Using the salt data, the alert suggests vetted suppliers or generic alternatives to restock.
Why this stands out for a software lab: Moving from simple CRUD operations (updating a number) to a ledger-based system (logging transactions) demonstrates strong software engineering principles. It accurately reflects how real-world warehouse and pharmacy management systems maintain data integrity.

Response: Yes, it will work completely fine. What you are describing is a decoupled architecture (or client-server architecture), which is the industry standard for modern web applications.
React and Flask do not need to be in the same folder, run on the same port, or even be hosted on the same server to work together.
Here is exactly how they communicate during both development and production:
1. During Development (Running Locally)
When you are building the app on your laptops, you will literally run two separate servers at the same time:
            * The Frontend: You run npm run dev in your React folder. Vite starts a server on http://localhost:5173.
            * The Backend: Your teammate runs python app.py (or flask run) in their Flask folder. Flask starts a server on http://localhost:5000.
React simply makes HTTP requests (using fetch or axios) across the network to http://localhost:5000/api/inventory.
The only catch (CORS): Because they are on different ports (5173 vs 5000), your browser will block the request for security reasons. Your teammate simply needs to install and add two lines to their Flask app to allow React to talk to it:
from flask_cors import CORS

app = Flask(__name__)
CORS(app) # This allows your React app to communicate with Flask

2. During Production (When you deploy the project)
When you are ready to submit the project and put it live on the internet, Vite makes this incredibly easy.
When you run the build command in React:
npm run build

Vite does not need Python or Flask to do this. It takes all your React code and squashes it down into pure, static HTML, CSS, and JavaScript files inside a dist/ folder.
You then have two standard options to host it:
            * Option A: Separate Hosting (Highly Recommended for Labs) You drag and drop your React dist/ folder (or connect your GitHub repo) into a free static host like Vercel or Netlify. Your teammate hosts the Flask API on a free server like Render or Railway. You just update your React code to fetch from [https://ak-medicines-api.onrender.com](https://ak-medicines-api.onrender.com) instead of localhost:5000.
            * Option B: Unified Serving If your professor requires everything to run from one single click/server, you take the contents of that React dist/ folder and paste them into Flask's static/ and templates/ folders. Flask then serves the React HTML file to the browser, and handles the API requests itself.
Because you are separated by HTTP requests (the JSON contract we defined earlier), React does not care what language the backend is written in, or where it lives, as long as it gets the right JSON back.

Project Overview & Problem Statement Medical NGOs and humanitarian aid field clinics operate in resource-constrained environments where medication availability directly impacts patient care. Solution & Architectural Highlights AK Medicines is a transaction-driven inventory management and automated alerting platform purpose-built for medical NGOs:
               1. Immutable Audit Ledger: Inventory is never modified by overwriting a static quantity. Instead, live stock is computed dynamically from an append-only ledger of discrete transactions:
Current Stock=∑Intake Quantity−∑Dispensed Quantity
This provides an unforgeable historical audit trail, enforces real-time overdraft protection, and supports point-in-time auditing.
               2. Clinical Salt Tracking & Generic Sourcing: Every medication is indexed by its brand name, therapeutic category, and active chemical salts (e.g., Augmentin 625 Duo → Amoxicillin + Clavulanic Acid). When a branded drug runs low, the system maps its active salts to registered wholesale generic vendors for rapid restocking.
               3. Automated Stock Health & Alert Engine: Supplies are continuously evaluated against customizable safety thresholds (default: 25 units) and categorized into Ample, Low Stock, or Depleted states, triggering immediate UI warnings and automated email notifications.

Slide 2: Problem Statement
Subtitle: Why Medical NGOs Need a Different Inventory System
                              1. Unaccounted Loss & Shrinkage (The "Mutable Quantity" Problem)
                              * Overwritten History: Traditional spreadsheets and basic CRUD apps overwrite a single quantity column (UPDATE medicines SET quantity = 80).
                              * Zero Accountability: They erase critical audit trails: Who took the medicine? Which clinic or camp received it? When did it arrive?
                              * Donor Compliance Risk: NGOs rely on external grants (WHO, Red Cross, donors) and must produce an unforgeable audit trail for every unit received and dispensed.
                              2. Brand vs. Chemical Salts (Procurement Bottlenecks)
                              * Brand Lock-In: When a commercial brand (e.g., Augmentin 625) runs out, field clinics lose critical time if the catalog only tracks brand names.
                              * Generic Equivalents: Staff need systems indexed by active chemical salts (Amoxicillin + Clavulanic Acid) to source generic equivalents immediately.
                              * Inconsistent Naming: Manual text entries vary in casing, spacing, and ingredient order, breaking naive database searches.
                              3. Delayed Shortage Detection (Reactive vs. Proactive Care)
                              * Point-of-Care Stockouts: Field clinics frequently discover a vital medicine is depleted only when a patient requires it.
                              * Disconnected Sourcing: Even when shortages are spotted, staff must manually cross-reference supplier spreadsheets to find who stocks that generic salt.
                              * Need for Automation: Clinics require real-time threshold alerts mapped directly to vetted wholesale suppliers.
Slide 3: Project Scope & Limitations
Subtitle: Core System Capabilities and Current Boundaries
Project Scope
                              * Immutable Double-Entry Audit Ledger: Stock is never manually edited; it is dynamically computed from append-only RECEIVE (Intake) and DISPENSE (Outward Issue) events: Current Stock=∑RECEIVE−∑DISPENSE.
                              * Active Salt Normalization & Supplier Matching: Automatically normalizes chemical formulations (case-, spacing-, and order-insensitive) to filter intake suppliers and recommend wholesale vendors when stock runs low.
                              * 3-Tier Stock Health & Dual Alerting: Classifies stock into Ample, Low Stock (< threshold, default 25), and Depleted (0), triggering both immediate email alerts on dispensation drops and 6-hour scheduled reminders.
                              * Role-Based Access Control (RBAC) & Donor Compliance: JWT-authenticated NGO admin and staff roles, plus 1-click CSV Audit Ledger Export and Bulk CSV Medicine Ingestion.
Current Limitations
                              * Batch-Level Expiry & FEFO Tracking: Currently tracks aggregate stock per medicine formulation rather than per-batch expiration dates (First-Expired, First-Out).
                              * Single-NGO Deployment Instance: Designed for a single NGO's centralized warehouse dispatching to multiple field clinics rather than a multi-tenant cross-NGO marketplace.
                              * Cloud Free-Tier SMTP Restrictions: Free cloud hosts (Render Free Tier) block outbound port 587 (smtp.gmail.com), requiring local SMTP execution or an HTTPS email relay in production.
